# Keyboard vs controller drifting (research for a future fairness option)

Written 2026-10-21, read-only research. Nothing was run in game and no source was changed.
Labels: **C** = confirmed in bytes or Ghidra decompile of `re\bin\SSASR-unpacked.exe`; **I** = inferred (reasoning, not proven).
Raw decompiles and scripts: `re\kbd-drift\` (`out\d*.txt`, `scripts\`). The Ghidra project was a scratch copy outside the repo.

## In plain words

- The game has **no separate "controller drift" feature**. I found no code that treats keyboard and controller differently, and "Drift+" is not in the exe. The car's physics **cannot tell the devices apart: any difference you feel comes from the steering numbers**. Keyboard steering is only ever -1, 0 or +1, and changes instantly; a stick gives every value in between (but nothing below about a quarter of the way, because of the pad dead zone).
- Your keys (arrows steer, **D gas, S drift**) are exactly the game's default bindings that I decoded from the exe (S is the *brake* input, which doubles as the drift button), so the code I traced is the code you are playing with.
- To start a drift the game wants **gas held + the drift (brake) key held + steering past a per-car threshold**. Letting go of the drift key ends the drift on purpose and gives the boost (the car enters a "releasing" state). While drifting, the amount of steering feeds straight into the drift angle of the car.
- **What you reported (latest wording):** the "auto-align" starts **the moment S is up**. You start the next drift so fast (S is up only about 0.09 s, section 2c) that the car never finishes straightening and stays sideways. If you waited, the car would end up straight and you would be steering into the wall. Earlier you said releasing the arrow first, then S, then pressing the arrow, then S gives the most seamless turn. **My reading of the release-phase code does not explain the arrow-order part** (section 2b), so the mechanism is unconfirmed. The fixes below are built so they do not depend on it.
- **You have no controller**, so "a controller keeps its direction" is secondhand (from other players or videos), and nobody here can test the controller half of the rules. The keyboard half can be tested by you; the controller half needs a friend with a pad (an internet race already works) or has to rest on the "same numbers give the same physics" argument.
- **Keyboard fix (Option A, section 3):** the thing you actually want is "stay sideways through the S tap". Two small automatic helpers, both only for the keyboard player and both host-controlled: **A3 tap-shortening** (when you tap S while an arrow is held, the S-up time seen by the game is cut to a couple of ticks, so the car has even less time to straighten, but the boost still happens) and **A2 release-macro** (an automatic version of your arrow-S-arrow-S order). Plus A1, a softer hold when only the arrow is released inside a drift. No code bytes.
- **Controller rule (section 3b):** because the physics only sees numbers, snapping the stick to full/none while drifting and during the boost gives the controller the keyboard's numbers, so it should behave the same. Untestable here without a pad (see above).
- Host on keyboard: controller players get the snap. Host on controller: keyboard players get the keyboard fix (section 3c).
- A test for anyone with a controller: push the stick **all the way** over and release the drift button; then do it with the stick only **half way** over. If the full-lock case auto-aligns the same way, magnitude is the cause and the snap reproduces it exactly.

## 2. What ends or straightens a drift, and why a stick avoids it

Drift state transitions in `0x5cb4b0` (all C unless marked):

- **0 -> 1** (or 3/4 -> 1, never from 2): `CanStartDrift` (gas + brake + steering past threshold).
- **State 1 (entry)**: reads the **raw** steer, keeps a latch at `vehicle+0x2a0` of the **largest same-direction magnitude** (the opposite direction never flips it in this build because the stubs return 0). After the hop timer `vehicle+0x270 >= tuning B (+0x230)` -> **state 2**.
- **State 2 (drifting)**: the car's body angle is `vehicle+0x250 + vehicle+0x210` (rotation built by `0x673d90`), and **`vehicle+0x250 = (tuningB(+0x1d0) * filteredSteer + clamp(vehicle+0x230, +-1) * tuningB(+0x1e0) + vehicle+0x250) * k`**. So the filtered steering number is a direct drive on the drift angle. No steering -> that term is gone and the angle relaxes: **this is the "auto-align" you see.**
- **2 -> 3** when any of: `racer+0xa60` (I: speed) below tuning B `+0x2a0` (I: minimum speed); All-Star active; **brake not held while the global byte `0x6ec732` is non-zero** (the byte is 1 in the game's memory dump, so "release brake = end the drift", i.e. the boost release); a stunt timer (`racer+0xad0`) running with a small slip angle.
- **3 -> 0** (`0x54dd30` resets every drift field): when the slip angle `|vehicle+0x260| < 1/16` and the drift angle `|vehicle+0x210| < 1/32`, i.e. the car is nearly straight again. Also reset by stunts, hits and respawns (`0x4ee436`, `0x4f0774`, `0x4f08b9`, `0x4f0b7c`, `0x4f2032`, `0x4f2938`, `0x4f2f05`).

So with **brake still held**, releasing the steering key does **not** by itself leave state 2 (no such test found): the car straightens because its drift angle loses its steering drive, and it is "redone" by pressing steering again (state 3 or 0 -> 1 restarts the hop). If the player lets go of both, state 3 then exits as soon as the car is straight. **This reading is partly inferred; the live check is open question 1.**

Why a stick avoids it: a stick at, say, 0.5 keeps `raw = 0.5`, so `target = 0.25` is steady, the lag filter holds `C ~ 0.25`, and the drift angle keeps a steady middle value. The return-to-centre branch (`|raw| < 0.25`) only triggers when the stick is nearly centred. A key can only give 0 (return-to-centre every tick, so `C` falls by `p1*f` per 20 ms) or 1.0.

## 2b. The release / boost phase (the user's report, 2026-10-21)

The report: arrows steer, D is gas, S is drift. Releasing S with the arrow still down gives the boost, but the car auto-aligns. To avoid it the user releases the arrow, then S, then presses the arrow, then S, fast, before the alignment is complete. A controller keeps its direction through the release.

What the code does there (state numbers as in section 2):
- **Release** = the brake-hold timer `vehicle+0x310` falls to 0 while the global byte `0x6ec732` is 1 -> drift state 3 (C). The boost itself is **not** granted by the native drift code (the only direct caller of the native boost starter `0x4e5f40` is the boost updater `0x4e9780`), so it is most likely granted by the scripted behaviour layer from the drift data (I).
- **Steering still enters in state 3**: while the speed is above the minimum, the slip-angle target is built from the filtered steering, roughly `0.5 * base angle * C^2` (`C` = the part of `racer+0xa90` selected by the sign of the slip `vehicle+0x260`; C: the `state == 3` block of `0x5cb4b0`; the sign convention is I). With no steering the target is 0 and the car swings back in line.
- **State 3 ends** (fields reset by `0x54dd30`) when `|slip| < 1/16` and `|drift angle| < 1/32` (C), i.e. once the car is straight. Stunts, hits and respawns also end it.
- **Drifting again** from state 3 or 0 needs only: gas held, S pressed again (`vehicle+0x310` counts up from 0 once the key is down), `|raw steer|` past tuning A `+0x170`, and, only if the state is already 0, `|filtered| <= |raw|` (C: `0x551940`). On paper the arrow does not have to be re-pressed.

What can be said safely:
1. **The physics only sees numbers.** A held arrow is raw `1.0` exactly (filtered value `C` goes to 1.0); a stick is anything up to 1.0 (and `C = raw^2`, so a half-pushed stick gives `C = 0.25`). Since the user says the controller does not suffer, the difference is in the **value** (full lock, `C = 1`) or the **instant edge**, not in the device.
2. **My formula for state 3 predicts the opposite** of the report (a bigger `C` keeps *more* angle). So either I have the sign convention of that block reversed (steering into the drift counting as "against" there), or another term dominates (for example the yaw drive `vehicle+0x250 = (tuningB(+0x1d0) * filtered + ...)`, whose gain sign I could not read from the code because the per-car numbers are data). **The mechanism is unresolved**; trust the report over my reading.
3. The user's workaround (steering 0 at the moment of release, then pressing again) works, so the **fix can copy the workaround without understanding the mechanism**: that is the "release-macro" in Option A2 below.
4. Equal numbers give equal physics, so the **controller nerf can copy the keyboard without understanding it either**: give the pad the keyboard's numbers (section 3b).

**Two cheap checks** before building anything: (a) the controller full-lock vs half-lock test in "In plain words"; (b) the 50 Hz log in open question 10.

## 2c. Measured key timing (free-driving log, 2026-10-21, with the user's OK)

A read-only logger recorded only Left, Right, D and S (down/up with timestamps) for about 2.7 minutes of ordinary driving. The user was not labelling "normal" vs "workaround" releases, so this is the user's habitual pattern, not a controlled test. The raw log and the logger were deleted afterwards; only these totals are kept.

- **S is tapped, not released for long.** 31 quick S taps (up then down again): the key is up for a median of **88 ms** (78-184 ms), which is only **about 4-5 physics ticks** (20 ms each). Before each tap S was held a median of **1.58 s** (1.2-2.5 s): this is the user's drift-and-boost chain rhythm.
- **An arrow was held at 34 of the 40 S releases**, but the arrows move a lot around the tap: an arrow was **pressed within 150 ms before the S release in 18 of 40**, **released within 150 ms before in 7 of 40**, and within 400 ms after S came back down an arrow was **released in 26 of 31** and **pressed in 21 of 31** (usually switching to the other direction).
- **What it means for the fixes**
  - The "release phase" the game sees is tiny: about 4-5 ticks with S up. Any rule that works on it must be tuned in ticks (the zero-steering window of the release-macro, A2, should cover about that S-up time: roughly the 2-tick lead plus 4 ticks), and a long "boost phase window" is not needed.
  - Because the user constantly switches arrow direction around the tap, the macro must never fight a direction change: any new arrow press cancels it at once and passes through.
  - For the pad nerf (3b) this means the snap has to be in force through those few ticks and the restart, not only during the long hold.
- **Still missing** (the user says the alignment starts as soon as S is up and a fast re-press cuts it short, so it probably is not a clean yes/no per release): which of those 40 releases auto-aligned and which stayed seamless. A labelled run would give it (for example 60 s of normal releases, then 60 s of the workaround, announced to me in that order).

## 3. Candidate fixes (project style: no code bytes, nothing the Roster Pack fingerprints)

The Roster Pack fingerprints 12 ranges (NATIVE-BRIDGE.md section 1: `0x4d4c14`, `0x4ba870`, `0x5b09a0`, `0x4d3d10`, `0x4d3ba0`, `0x4d4ea0`, `0x54bb00`, `0x4900bd`, `0x5fe690`, `0x6f6a88`, `0x6f6620`, `0x6f661c`). Every address below is outside them.

### Option A (recommended): "Keyboard drift hold", wrapper on the Human state update

- **Hook**: replace the data slot `0x6b1b8c` (`50 f1 5a 00`, the Human state's update, only a data reference) with our thiscall wrapper. Same slot-swap method as the M2/M3 hooks; check the 4 original bytes first.
- **Wrapper** (after calling the original `0x5af150`, so the CS is complete):
  1. Only when the rule is on.
  2. Is this player on the keyboard? `CS[0]` (`[controller + 0x1c]`) is the player's **device index**: the racer's `+0x9ec`, copied there when the controller is made (C: `0x4e6110`, `[controller+0x1c] = [racer+0x9ec]`), i.e. the third argument of native `0905` (I). The device list is 4 XInput pads (index 0..3) then the keyboard (**index 4**), with the mouse kept apart (C: `0x406e00` appends in that order and stores the keyboard at `mgr+0x4c`). So **keyboard player = `CS[0] == 4`** (the keyboard half is C; "the lobby's pad index is the same number" is I, see section 3b). A belt-and-braces check is the device's vtable: `dev = [mgr + 0xc + 4*CS[0]]`, `mgr = [[0xc2a1b4] + 0x14]` (C: the expression `0x5af150` uses); keyboard when `[dev] == 0x67e444`. I found no code path that changes `CS[0]` during a race (I), so there is no mid-race device switch to handle.
  3. `vehicle = [racer + 0x9f4]`; if `[vehicle+0x2d0]` is 1 or 2 **and** `[vehicle+0x310] > 0` (brake held):
     - while `|CS.steer| >= 0.5`, remember its sign;
     - if `|CS.steer| < 0.5` (key released) and a sign is remembered, write `CS+0x40 = sign * H`.
  4. Forget the remembered sign when the state is not 1/2, brake is released, or the opposite key is pressed (that passes through unchanged and re-latches).
- **H** (hold level): config/rule value, start with **0.7** (target `0.7^2 = 0.49`, about half the drift drive). Tune with a controller side by side.
- **Why it is safe for the rest**: it only runs in drift states 1-2 with the brake held, so it cannot start a drift (that is state 0/3) or stop one; it changes one float in the CS that the game already treats as analog.
- **Risks**:
  - Order inside a tick: the **controller/state update runs before the racer physics** (C: `notes/RACE-BRIDGE.md` "Sim step order"), so the wrapper's value is the one `0x4e7da0` and the drift update read in the same tick.
  - Other readers of the same steer value: lean/wheelie `0x4e90f0`, the replay/ghost recorder `0x504420`, camera `0x551940`. They would see the held value too (probably wanted).
  - Other mods that hook drift code (Ten Stage Drift, Honest Gauges) are not touched, since we only change the input number. Ten Stage Drift is currently disabled.
  - Held 0.7 could feel "sticky" in a tight hairpin. The opposite key always overrides.
  - Remote cars are pose puppets (M3/M4): nothing to sync for the effect itself.

- **A3 (new, from the user's latest wording): "tap-shortening".** The user wants to stay sideways through the S tap, and the alignment starts the moment S is up (state 3). The S-up time is the only thing the car has to straighten in, so make it shorter without losing the release: when S falls to 0 **while an arrow is held** (the player is clearly continuing the turn) and a drift was running (state 1 or 2), let the release through for **K ticks** (suggest K = 2, i.e. 40 ms; the user's own taps are about 4-5 ticks), then force `CS+0x48` back to its old value (a virtual re-press) while the physical key is still up, up to a cap (suggest 8 ticks, 160 ms); if S is still up after the cap, release for real (the player means a longer release). No arrow held means no virtual re-press, so a deliberate release to straighten is untouched. The user confirms the boost is instant on release (needs a charged gauge), even for the shortest taps, so K = 2 is fine. Still to be checked live: (1) ~~whether the boost is still granted when state 3 lasts only K ticks~~ (answered: yes) (the boost is granted by the script layer, I; if it needs a minimum time, raise K); (2) that the restart (state 3 to 1) happens on the first tick after the virtual re-press. The brake value is read from `CS+0x48` by `0x54e010` each tick, so changing it in the wrapper is enough.
- **A2 (revised after the user's report): "release-macro", an automatic version of the user's trick.** Keep the last tick's brake value and the arrow state. When the drift key falls to 0 while an arrow is held and the drift state was 1 or 2 (so a drift was running), run a short sequence on the keyboard player's inputs:
  1. For about 2 ticks keep `CS+0x48` (brake) at its old value and feed `CS+0x40 = 0` (the game sees "arrow up" first, as in the manual trick);
  2. then let the brake release through (boost starts, about 40 ms late) while still feeding steering 0 for N1 more ticks (suggest N1 = 4, i.e. about 0.1 s in total);
  3. then give the held arrow back at full. If the player presses S again during the zero window, end the window at once: restore the arrow one tick before the S press passes (arrow down, then S down, like the manual trick).
  This reproduces exactly the input order the user found to work ([arrow up, S up] then [arrow down, S down]), with tick-perfect timing, whatever the mechanism is. N1 and the 2-tick lead are guesses to tune with the user, who knows the right feel.
  *Variant "release-soften"*: feed a part-pushed value (about 0.4) instead of 0, closer to what a stick does. Try 0 first, because 0 is what is known to work.
  Risks: the boost starts about 40 ms later; a player who really wants to straighten at the boost loses nothing (steering is neutral for 0.1 s, then the held arrow resumes, and they can release it); A1 and A2 never fight (A1 acts only with S held, A2 only around its release).

### Option B (simpler, wider): "Keyboard analog smoothing", same hook

- Same wrapper and keyboard check, but always (not only in a drift): ramp `CS.steer` toward the key value (-1/0/+1) at a limited speed (for example attack 6/s, release 4/s) so a short tap gives a partial value and a release fades instead of dropping to 0.
- **Pro**: no vehicle fields read, so nothing to misread; helps normal steering too.
- **Con**: changes the feel of every corner and slightly delays the drift start (the drift needs `|raw| > threshold`); does not truly "hold" a drift, it only softens taps.

### Not recommended: flip the two digital-pad stubs (`0x508170`/`0x508180`)

They are code and global (no player argument), so they would affect controller players too, and the effect of the alternate paths was not worked out. Listed only as a lead.

### As a lobby rule (the same for everyone)

- New host option **"Keyboard drift hold"**: Off (vanilla) / On (level H). The host's value is what every PC uses (like the `HostRunsAI` contract flag and the host's items/AI rules from M5), and it is shown in the lobby Settings.
- Each PC applies it **only to its own local keyboard-driven car**; controller players keep their analog stick as is. Result: every keyboard player gets a stick-like drift hold, every controller player already has it. Nothing needs to be sent for the simulation (each PC drives its own car); only the agreed setting travels in the lobby data / contract flag (a wire version bump if it goes into the race contract, like `HostRunsAI`).
- Codex's idea of "disable controller Drift+ when a keyboard racer is present" is **not possible as a switch**: there is nothing to turn off, only a stick that is naturally analog. The closest honest version is the fallback in section 3b below (make controller steering digital while a keyboard player is in the lobby).

## 3b. Fallback rule: controllers steer like a keyboard when a keyboard player is in the lobby

Asked for by the user (2026-10-21): if the keyboard cannot be given a sustained drift, make controller players feel the keyboard way instead. This is feasible with the same hook and no code bytes. All C unless marked.

**Revised after the user's report (section 2b):** the physics cannot tell devices apart, so the faithful way to make a pad behave like the keyboard is to give it **the same numbers**: snap `CS.steer` to -1/0/+1 while it matters. The keyboard's auto-align on release comes from holding full lock (and instant edges) through the release; a snapped pad holds exactly that, so it should show the same auto-align. (A previous draft proposed a "release-cut", steering forced to 0 after the drift button is released. That is the user's own workaround for the keyboard and would help the pad, so it is dropped.) The snap must therefore also cover the **release phase** (drift state 3), not only the held drift.

**Testability:** the user has no controller, so this half cannot be checked on this PC. It is justified by construction (the same `CS.steer` numbers into the same physics) and should get one test with a friend who has a pad before it is trusted.

**What "like a keyboard" means in the game's numbers.** The keyboard puts exactly `-1`, `0` or `+1` into `CS.steer` (`0x5af150`: RIGHT - LEFT, each key 0.0 or 1.0). Everything after that (signed square, lag filter, return-to-centre when `|raw| < 0.25`, drift start/latch/yaw drive) is shared. So if a pad player's `CS.steer` is snapped to the same three values, **the rest of the game behaves for them exactly as for a keyboard player**: release = 0 = return-to-centre every tick = the drift angle melts, hold = full lock.

**Where to hook** (best first):
1. **Same wrapper as Option A** (Human update, data slot `0x6b1b8c`), after the original runs. For a local human whose `CS[0] != 4` (pad, wheel, joystick) and with the rule active, rewrite `CS+0x40`:
   - snap with hysteresis: switch to `+-1` when `|x| >= 0.55`, back to 0 when `|x| < 0.35` (a keyboard has no in-between, so any threshold is a design choice; the pad code already zeroes `|x| < 0.24`);
   - two strengths: **drift only** (only while `[vehicle+0x2d0]` is 1, 2 or 3, i.e. a drift or its release/boost phase, so normal steering stays analog; this matches the complaint and is the suggested default) or **all steering** (always snapped; heavier, although a keyboard player's normal steering is also softened by the lag filter, so a snapped pad is not as harsh as it sounds);
   - one wrapper serves both rules (Option A for keyboards, this one for pads), selected by the rule value.
2. **Pad poll wrapper** (data slot `0x67e408` = XInput pad poll `0x405dc0`; the DirectInput joystick class has its own vtable `0x67e39c`): after the original, snap the stick-X channel (channel 11, `+0x2c` of the device buffer) before the Human update reads it. Also simple, but it cannot be "drift only", and it snaps the stick in menus too (menus use the stick through the 0.6 thresholds of `0x5a48d0`, so mostly harmless). The D-pad channels are already digital.
3. *Not recommended*: code patches such as the `0x508170/0x508180` stubs (global, no player argument).

**How the game knows each player's input device (lobby member data).**
- Each PC already receives its **primary pad index** from the lobby script every frame (native `0400`, `PRIMARY_PAD` in `tools\netmenu\steam.py`; stored as `g_localPad` in `src/natives.cpp`; it is also the number the race start sends `fe_game_bridge` as that player's device, which `0905` then receives; it reads hash 0 until a pad is assigned). Index `4` = keyboard, `0..3` = pads (keyboard half C, see Option A step 2).
- Publish it like `racer`/`ready`/`net`: one more member datum, e.g. `inp` = `k` (index 4) or `p` (anything else), written in `WriteLocalData()` (`src/steam_mp.cpp`) and read in `ReadLobbyData()`; add `inp` to `LobbyMember` (`src/lobby.h`). The race-time check needs no lobby data at all: it is `CS[0] != 4`.
- **Host decides once, at Start.** `anyKeyboard` = any member (host included) with `inp == k`. The host puts the resolved rule into the race contract (a flag in `src/race_wire.h` next to `HostRunsAI`, which means a wire version bump) so every PC applies the same rule for the whole race. A member leaving or changing device mid-race does not change it (this answers Codex's "do not let a device switch silently remove the restriction"); the next race re-evaluates.
- Rule values for the host: `Off`, `Keyboard drift hold` (Option A), `Pads steer digitally when a keyboard is present (drift only)`, `... (all steering)`. A new lobby datum (e.g. `inprule`) avoids touching the 6-field `rules` string. The Settings screen would need one more row, and the lobby frame script chunk is near its 16-bit jump limit (`notes/RACE-BRIDGE.md` section 7: 440 of 594 free bytes used), so a first version can be `config.ini` on the host plus a lobby text line.

**Risks.**
- **Feel and consent**: it is a real handicap for pad players. Show it clearly in the lobby ("pads steer digitally: a keyboard player is in this lobby"), keep it host-controlled and off by default.
- **Threshold choice**: 0.55 / 0.35 is a guess. Too low turns light touches into full lock; too high under-steers. A stick also cannot copy the keyboard's instant 0-to-1 edge (it takes a moment to cross the threshold), so a snapped pad is slightly more forgiving than a key. Needs a side-by-side test with a keyboard player.
- **Device identification**: `4 = keyboard` and "the lobby's pad index equals `0905`'s device" come from reading code and from Codex's trace ("device argument is 4"); neither is verified in a live run (I). A user with a pad connected who plays on the keyboard is classified by the primary index, not by what they press. A wheel or joystick counts as a pad (snapped too).
- **Trust**: devices are self-reported member data; a modified client can lie. Same trust level as the rest of the mod.
- **Overlap with Option A**: they target different devices (A: keyboard only, 3b: non-keyboard only), so a lobby uses one or the other, not both.
- **Menus and other screens** are untouched with hook 1; hook 2 touches the stick in menus.
- **Other readers of `CS.steer`** (lean `0x4e90f0`, replay recorder `0x504420`, camera) see the snapped value, as they do for a keyboard.
- **Remote cars are pose puppets**, so nothing about the rule needs to travel during the race.

## 3c. Combined rule: "Match the host's input" (the user's idea, 2026-10-21)

One lobby option, **Input fairness: Off / Match host**. At Start the host looks at its own device and the whole lobby follows it:

| Host plays | Rule that applies | Who is changed | How exact |
|---|---|---|---|
| **Keyboard** | 3b: pads' steering is **snapped to full/none** while drifting and during the release/boost phase | every controller player | close to exact: same numbers into the same physics; the human side (key rollover, hand speed) cannot be copied |
| **Controller** | Option A: keyboard **release-macro (A2)**, plus the drift hold (A1) | every keyboard player | approximate: it replays the user's own workaround with fixed timing, so it needs tuning |

Players already on the host's device type are never touched, and if every player uses the same device type the rule does nothing.

**Why it is easy on top of what is described above**
- Same single wrapper on the Human update slot `0x6b1b8c`; the rule value is just "digital pads" or "keyboard hold", picked from the host's device.
- Host device = the host's own `inp` member datum (primary pad index 4 = keyboard, else pad), read at Start by the host and written into the race contract as a 2-value flag (0 none, 1 pads digital, 2 keyboard hold). Players do the per-tick check `CS[0] != 4` or `== 4` against that flag. Frozen for the race, re-evaluated at the next Start.
- Lobby text: "INPUT: MATCH HOST (KEYBOARD)" or "(CONTROLLER)", plus a one-line notice to the affected player ("your steering is digital: the host plays keyboard").

**Extra things to watch**
- Host classification relies on the primary pad index. A host with a pad plugged in who plays on the keyboard (or the reverse) must be classified by what they actually use; check with the log line in open question 7. If the primary index turns out unreliable, use "last device with input" instead (the mod already wraps both polls for background running).
- The two halves are not equally exact (see the table), so test them separately; the first one is the safer one to ship first.
- If the host leaves the lobby the rule is moot (lobby ends today); with a future host-migration feature the rule would re-resolve at the next Start from the new host.
- A wheel or joystick counts as a controller.
- Mixed single-device lobbies (host keyboard, two keyboard guests, one pad guest): only the pad guest changes.

## 3f. The cause (reverse-engineer pass 2026-11-09, `re\drift-cause\FINDINGS.md`)
**§3e's grouping had a sign error: its "held INTO the turn" releases were counter-steer releases.** The game treats both devices the same. The "swing across" is a new drift on the other side: S re-pressed within a few ticks while the counter arrow is still down (the new hop latches -steer on its first tick, 0x5cbda1). A keyboard does it far more often only because this player taps S fast (42/59 quick re-presses vs the pad's 11/34) and a key's counter-steer is always 1.0, above the 0.65 hop threshold. In state 3 only steering toward the drift's own side holds the angle (0x5cc3ab). Fix options: (1) same-side tap: on a quick re-press with the counter arrow held through, steer the hop's own way for that one tick; (2) cap a held-through counter arrow at 0.6 in state 3. Both keyboard-only, both drop dp1's remap. **Next: show the user, then a labelled 2x2 test** (keyboard / pad x quick tap holding the hop arrow / the counter arrow) to confirm that the counter-arrow tap is what they feel. **The user's OK (2026-11-09, "Yes, allowed"): the fix may also change the quick drift re-press, not only the release.**
